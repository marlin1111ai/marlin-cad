# Decisions

Design decisions and the reason for each.

- **Foreman/builder workflow, print-gated phases.** Claude (chat) is the foreman — plans, writes specs, reviews reports. Claude Code is the builder — implements on the Linux box. Phases are print-gated: a coupon or sampler is printed and hand-verified before the next phase builds on it.
- **Boundary-rep/earcut over runtime CSG.** Runtime CSG subtraction is unreliable for cuts that reach a surface and is slower; boundary construction is dependable and dramatically faster. See CLAUDE-LESSONS.md.
- **UI scoping over code deletion.** Board Type is restricted to "full" and Heavy is hidden in the UI rather than removing the underlying code, since the variants aren't validated yet.
- **Wrench Racks presets must stay byte-identical to test-prints/ reference STLs.** Those STLs are the physically validated exports; any geometry change that alters them requires a new print verification pass before merging.
- **Multiconnect slots are blind keyhole cuts, 4.15mm deep.** The front face stays solid by construction.
- **plateThickness extra material goes frontward.** Slots are always measured from the mounting face, so added thickness doesn't change slot depth.
- **Peg x is "from the left edge as mounted."** User-facing peg positions are specified in as-mounted view space; geometry mirrors internally at exactly one marked spot (`normalizedPegs`), since the front face is X-mirrored relative to geometry space.
- **Shelf variant intentionally has no truss/gusset.**
- **MIN_OPENCONNECT_DIMENSION lowered to 0.1** (`97a97a3`).
- **Deployment to Unraid is a separate, human-gated step.** Dev runs as a local process on port 3000.
- **`deploy/docker/Dockerfile` is canonical; the root Dockerfile was removed.** Every build path already targeted it — `npm run docker:build`, `deploy/docker/compose.yaml`, and `.github/workflows/docker.yml` all pass `file: deploy/docker/Dockerfile` with the repo root as context — so a second root Dockerfile was pure drift risk (`edb8101`). The root `.dockerignore` went with it: BuildKit reads the ignore file sitting next to the Dockerfile, so `deploy/docker/Dockerfile.dockerignore` is what applies and the root file never did.
- **Production images publish to GHCR; Unraid pulls from there.** Matches the pattern already used by the other Marlin apps, and keeps the NAS out of the build business.
- **Unraid pins a version tag (currently `1.3.3`), never `:latest`.** Production moves only when the tag is changed deliberately; Unraid's update check cannot pull a new build out from under a working deployment. Since `2c3767d`, the version tag is re-pushed on every push to `main`, so the tag name itself is not immutable — but Unraid still only moves when the owner changes the tag in the container config or applies an update, since it isn't watching `main`.
- **Images are built by GitHub Actions and tagged with the `package.json` version; the Linux dev box never runs Docker.** Owner's process: Claude Code publishes to GitHub, the owner pulls on Unraid.
- **The GHCR package is public.** The image contains only the open-source app and its built-in presets, so there is nothing to gate — and public means Unraid does not need to hold GHCR credentials to pull.
- **marlin-cad is Linux-only.** Developed on Pop!_OS, deployed as a Linux container on Unraid. The Mac is browser and slicer only. Cross-platform moves (Mac/Windows/Linux) caused persistent problems on other projects; this one never left Linux and never had them.
- **Projects live on the `/Apps` drive, not in the home folder.** Runtimes (Node via nvm) and tooling stay in the home folder; project files and `node_modules` stay under `/Apps/<project>`.
- **Socket Tray is a flat tray with round blind pockets the sockets sit in, not posts; solid floor.** A round blind pocket is a strict simplification of the Multiconnect keyhole slot (no taper, no dimple, no baked mesh needed): the rim circle is notched into the top face's outline and the pocket's cylindrical wall and flat floor cap reuse the same rim/floor-ring points, so the seam is bit-identical by construction with no CSG. The floor under each pocket is 4mm, above the module's 2mm `MIN_SOCKET_TRAY_FLOOR_THICKNESS`, per the slicer-slit-fusion lesson: don't let a floor go arbitrarily thin just because the geometry permits it.
- **CORRECTED 2026-09-04 — the mounted tray's back is a Multiconnect slotted plate with no pegs, NOT the OpenGrid Snap.** This entry previously read "The Socket Tray back plate is the existing OpenGrid Snap primitive." That was wrong about the mating feature. The recon (`4eecc37`) established that the physically validated wrench racks hang on Multiconnect keyhole slots at 28mm spacing (`multiconnectPresets.ts`), while the OpenGrid Snap this app bakes is generated with an openConnect head — a different profile with different clearances. Upstream's snap generator does offer a multiConnect head, but no such variant is baked here. Owner's decision: the mounted tray's back is the same Multiconnect slotted plate the wrench racks use, carrying no pegs, so it hangs on the same connectors. Still true from the original entry: the flat sampler coupon is deliberately tray-only, a standalone block that does not attach to a board, and the Snap has no runtime attach function — Snap and Container/slot geometry are independently baked meshes sharing a head profile from the same upstream SCAD source.
- **The mounted tray is one L-profile prism, not a plate joined to a tray.** The plate and the tray are a single prism whose cross-section in the (Y, Z) plane is an L, extruded along the width. The L outline is built once as one six-point array, and both the extruded side faces and the two end caps read their corners out of that same array, so the junction vertices are bit-identical because they are the same doubles — there is no seam to stitch and no second construction path to disagree with the first. The recon had named that junction the primary ULP-mismatch risk; this designs it out rather than mitigating it. See `reference/reports/mounted-socket-tray-build.md` step 4 (`c98cff5`).
- **The mounted tray's slot channel is clear by construction.** The channel occupies only the rear 4.15mm of the plate, measured from the mounting face, and extra plate thickness moves the blind floor further back rather than toward the front — so a forward-projecting tray can never share its Z band at any height. The guarantee is carried by the 6.5mm minimum plate thickness (4.15mm cut + 2.35mm skin), enforced as a floor rather than a thrown error; no tray-placement rule was invented on top of it. See `reference/reports/mounted-socket-tray-build.md` step 2 (`c98cff5`).
- **The mounted tray is a separate shape and module; the flat Socket Tray is unchanged and remains the test piece.** Owner's requirement. `mountedSocketTrayGeometry.ts` is additive: it imports from `socketTrayGeometry.ts` and `multiconnectContainerGeometry.ts` but edits neither, and the flat tray's geometry, tests, coupon, UI registration and defaults are untouched (asserted by a registration test).
- **Standard-length sockets only; pocket depth 14mm; pocket diameter = measured OD + 2mm clearance.** Depth is sized for a 3/8"-drive standard (non-deep) socket, toward the shallower end of the roughly 12–25mm range, and is the one remaining estimate in the coupon. Diameters are real caliper-measured socket ODs plus a stated 2mm radial clearance, so the coupon tests both the diameters and whether 2mm is the right clearance.
- **The production tray has one pocket per socket (12), even where widths repeat.** The 6-pocket coupon groups sockets by shared pocket size (2/3/3/1/1/2) to test fit; the production tray does not share pockets.
- **Socket Tray width matches the wrench racks; the coupon targets the X1C bed only.** 240mm was originally a hard constraint matching the wrench rack plates' footprint. For the 6-pocket coupon it is the result of 30mm margins + 5×36mm pitch: six pockets at the old 45mm pitch would have needed 285mm, 29mm over the X1C's 256mm bed, so the owner approved reducing pitch rather than shrinking margins or diameters. 240mm leaves 16mm spare on the X1C.
- **Socket geometry is additive-only in `socketTrayGeometry.ts`; zero edits to `multiconnectContainerGeometry.ts`.** The Multiconnect module exports only plate-specific surface, none of it generic pocket-cutting infrastructure; the boundary-rep technique is a pattern to imitate, not a library to import, matching the existing one-primitive-per-file convention. Confirmed: `multiconnectContainerGeometry.ts` was read but never imported or edited across the socket commits (`88c37a1`..`cc4f3ff`).
- **Socket Tray pocket diameters are typed by the owner as the finished hole size; the app does no socket-size lookup.** The owner measures the socket OD with calipers and adds clearance, so it works for any brand or object.
- **One Pocket Depth for the whole tray, not per pocket.** Standard-length sockets only, 14mm default.
- **Pocket positions are explicit per pocket (X from the left edge, Z from the front edge); no auto-layout or pitch field.** The owner lays out the holes.
- **Socket Tray Thickness maps to the app's height axis; Width and Depth map directly.** Per the build report: the module's frame is X = width, Y = thickness (up, matching the app's Y-up scene), Z = depth, and the app's `height` field is its Y-up dimension; the Multiconnect plate maps its thickness to `depth` only because its thickness runs along Z (`fe3e829`).
- **Socket Tray pocket x is not mirrored — it runs the same direction the viewport shows it.** Per the build report's step-7 finding: the tray lies flat and its x is plain left-to-right geometry space; from the home camera increasing x moves right on screen, and no mirror is applied anywhere in the tray's render or export path. The Multiconnect mirror exists because its front face is viewed from the wall side, which does not apply here (`fe3e829`). **Still true for the FLAT tray only — corrected for the mounted variant below.**
- **CORRECTED 2026-09-06 — the MOUNTED Socket Tray's pocket x IS mirrored; the entry above applies to the flat tray alone.** The mounted tray originally inherited the flat tray's no-mirror rule, on the stated reasoning that "pockets open UPWARD on a horizontal shelf, so x runs the same direction the viewport shows it." That reasoning was wrong: opening direction is a Y-axis fact, while left/right is an X-axis fact about a rigid body whose orientation the wall mount fully determines. The mounting face goes against the board and the tray projects forward, so the viewer always stands at low Z looking along +Z — and a viewer looking along +Z with +Y up has +X on their LEFT. Geometry x = 0 is therefore the mounted viewer's RIGHT edge, exactly as on the Multiconnect plate. Symptom: a pocket typed at X = 30 rendered and would have printed near the right end. The flat tray's exemption genuinely does not carry over, because that tray is standalone with no fixed viewing side, whereas this one has exactly one valid mounting orientation (the slot channel runs down and out the bottom edge; the shelf projects forward). Fixed by mirroring at one marked spot in `normalizedPockets` (`x_geometry = plateWidth - x_viewed`), matching `normalizedPegs`. Slots needed no change — `mountedSocketTraySlotCenters` is mirror-symmetric by construction — and pocket z is unaffected. Both mounted coupon STLs were regenerated; the flat tray, its coupon and its tests were not touched.
- **Default Socket Tray insert is the six-pocket coupon.** It is the real starting point, and it doubles as the export regression check: the default insert through the real STL writer reproduces `test-prints/socket-tray-sampler.stl` triangle for triangle (`fe3e829`).
- **Socket Tray and Mounted Socket Tray corner rounding is a user-typed Corner Radius field, not a fixed constant; 0 is the default and is provably identical to pre-rounding output.** Matches how pocket diameters already work, and preserves the existing byte-identical regression path at radius 0 (`4be03de`).
- **Corner rounding uses a mitered quarter-arc technique, matching the existing Multiconnect peg fillet, not a fully blended 3D fillet, and not the app's separate runtime OCCT fillet tool.** Keeps the shape boundary-rep and testable the same way as every other socket-tray feature (`4be03de`).
- **The Mounted Socket Tray's plate-to-tray L-junction is excluded from rounding.** Owner's decision; that seam is structurally different from a simple edge (`4be03de`).
- **The Screwdriver Tray is a separate shape and module; both Socket Trays are unchanged and stay frozen.** Owner's requirement, and the same additive move the mounted tray made. A screwdriver hangs by its handle with the shaft passing THROUGH the tray, so the hole has no floor — but the owner chose two new sibling shapes over a per-hole blind/through toggle on the existing ones, because the socket trays are the print-gated shapes. `screwdriverTrayGeometry.ts` imports `SOCKET_TRAY_POCKET_EDGE_CLEARANCE`, `SOCKET_TRAY_POCKET_GAP`, `SOCKET_TRAY_POCKET_SEGMENTS` and `SOCKET_TRAY_FILLET_SEGMENTS` from `socketTrayGeometry.ts` read-only and edits nothing there, so "the same rule" is the same constant; the flat tray's geometry, tests, coupons, defaults and UI registration are untouched (asserted by a registration test).
- **The Screwdriver Tray's bottom rim is SHARP; only the top rim and the outer top perimeter round.** Owner's decision (option A of `reference/reports/screwdriver-tray-recon.md` section 4). The bottom face is notched with each hole's NOMINAL radius and there is no bottom fillet code in the module at all, so the straight-wall guard stays `cornerRadius < thickness` rather than tightening to `2 * cornerRadius < thickness`. Consistent with what both Socket Trays already do with their own bottom edges — the flat tray's bottom face is a full uncut rectangle at any radius and the mounted tray's two bottom corners are explicitly excluded — and it keeps the first printed layer's edges the shape every physically validated part in this repo has.
- **Minimum Screwdriver Tray thickness is 10mm, a new constant in the new module.** `MIN_SCREWDRIVER_TRAY_THICKNESS`, owner's number. It replaces the role `MIN_SOCKET_TRAY_FLOOR_THICKNESS` (2mm) plays on the socket trays, and that constant is deliberately NOT imported here: it guards material under a blind pocket, which a through-hole does not have. What a through-bore needs instead is enough length to hold a shaft upright — a 2mm tray would make a perfectly valid mesh and a useless part. Thrown, not clamped, and surfaced in the inspector as the Thickness row's minimum.
- **The Screwdriver Tray has no Pocket Depth at all — not per hole, not shared.** A hole is Diameter / X / Z; its depth IS the tray thickness. No `depth` field on the hole type, no `pocketDepth` option, no inspector row, and no floor-thickness or depth-vs-radius guards. The socket trays' `cornerRadius >= pocket.depth` guard collapses into the tray-thickness guard that already existed.
- **The Screwdriver Tray's default insert is 240 x 60 x 18mm with three holes at 8 / 10 / 12mm; the diameters are deliberate generic placeholders.** Owner's numbers. Holes sit on the z = 30 centreline at 30mm end margins, so the pitch is 90mm and the centres land at x = 30 / 120 / 210 — the same layout convention both socket coupons use. Unlike the Socket Tray's diameters (caliper-measured socket ODs plus a stated 2mm clearance) these are a starting point, not measured values and not a validated recipe; the owner types the finished hole size the same way, and nothing in the app looks a screwdriver size up.
- **No coupon STL or generator script was produced for the Screwdriver Tray.** Not approved for the build pass; `test-prints/` was untouched. The shape is therefore unprinted and unvalidated in the same sense both socket coupons are, but it does not even have a candidate file yet.
- **The Mounted Screwdriver Tray is a fourth separate shape and module; the other three trays stay frozen.** Owner's requirement, built as Pass B of a two-pass plan (Pass A was the flat Screwdriver Tray). `mountedScrewdriverTrayGeometry.ts` is additive: it imports the baked slot data from `multiconnectSlotMesh.ts`, the plate constants from `multiconnectContainerGeometry.ts`, the hole-layout guard constants from `socketTrayGeometry.ts` and `MIN_SCREWDRIVER_TRAY_THICKNESS` from `screwdriverTrayGeometry.ts`, and edits none of them. All three earlier tray modules were confirmed byte-identical (`git hash-object`) after the pass.
- **The Mounted Screwdriver Tray is one L-profile prism, exactly as the Mounted Socket Tray is.** Same single six-point outline array, same rule that the six extruded side faces and the two end caps read their corners out of it, so the plate-to-tray junction vertices are bit-identical because they ARE the same doubles. Copied rather than re-derived, because that construction is what designs the ULP-mismatch seam out rather than mitigating it; a dedicated inner-corner test isolates the junction line on the new mesh.
- **The Mounted Screwdriver Tray's hole x IS mirrored into geometry space.** `x_geometry = plateWidth - x_viewed`, at one marked spot in `normalizedHoles`, matching `normalizedPegs` and the Mounted Socket Tray's `normalizedPockets`. This shape has exactly one valid mounting orientation (the slot channel runs down and out the bottom edge, the shelf projects forward), so the viewer always looks along +Z and geometry x = 0 is their RIGHT edge. It deliberately does NOT inherit the flat Screwdriver Tray's no-mirror rule — that inheritance is precisely the bug that shipped on the Mounted Socket Tray and was fixed on 2026-09-06. Hole z is not mirrored, and the slot run needs no mirror (it is mirror-symmetric by construction). Pinned by an asymmetric test layout that asserts each bore's un-mirrored position is SOLID, so neither a missing nor a doubled mirror can pass.
- **The Mounted Screwdriver Tray's bottom rim is SHARP and its minimum tray thickness is 10mm.** Same two owner decisions as the flat Screwdriver Tray, and the 10mm is the same imported constant rather than a second copy. The bottom face is notched with each bore's NOMINAL radius, there is no bottom fillet code in the module, and `cornerFRoom = min(trayDepth, trayThickness)` — the guard the Mounted Socket Tray already had — is what keeps `cornerRadius < trayThickness` without needing a per-bore check.
- **The Mounted Screwdriver Tray's bores and slot channels share one earcut bottom cap and cannot collide.** The bottom face already carried one channel-notch indentation per slot; it now also carries one hole per bore. They are disjoint in Z by at least 7.35mm under every allowed parameter combination — the bore edge-clearance guard bounds bores at `trayDepth - 5` while the 6.5mm plate-thickness floor puts the channel no nearer than `trayDepth + 2.35`, and extra plate thickness only moves it further away. The slot-channel unobstructed check was re-run on the new mesh rather than assumed from the Mounted Socket Tray.
- **The Mounted Screwdriver Tray's default insert is the validated wrench-rack plate (240 x 60 x 10mm, 28mm spacing, 8 slots) with a 60 x 18mm shelf and three through-bores at 8 / 10 / 12mm.** Bores at viewed x = 30 / 120 / 210 on the z = 30 centreline, 30mm end margins, 90mm pitch. The diameters are the same deliberate generic placeholders the flat Screwdriver Tray uses — not measured shafts, not a validated recipe.
- **No coupon STL and no generator script was produced for the Mounted Screwdriver Tray either.** Not approved; `test-prints/` was untouched on both screwdriver passes.
- **The project-thumbnail guard reads the `Host` header, not the server's bind address, and accepts private-LAN IPv4 only (plus localhost).** Owner's ruling, 2026-09-09; shipped in `1.3.3` (`9e926bf`). Allowed hosts are literal IPv4 in 10/8, 172.16/12 and 192.168/16, plus `localhost` / `127.0.0.1` / `::1`; host names, `.local` names and public addresses stay rejected, the Origin must match the Host exactly (host and port together), a request with no Host is refused, and `X-Forwarded-*` is not consulted because nothing proxies the container. **Why:** `new URL(request.url)` can never match in production — Next derives it from the address the server bound to, which in the container is `0.0.0.0`, and Unraid publishes host port 3001 onto container port 3000, so even a correct hostname would carry the wrong port. `1.3.2` (`6ae02f7`) widened the range but kept reading `request.url` and was therefore a no-op on Unraid. **Tradeoff:** the Host header is client-asserted, so a client can claim any allowed host. Accepted because this endpoint's blast radius is a cache of PNG thumbnails (5 MiB cap, PNG prefix enforced, filename reduced to `[a-zA-Z0-9_-]`). The same reasoning does not transfer: `/api/local-download`, a 512MB arbitrary-path file writer, deliberately stays localhost-only, as does `codex-screenshot` — each route keeps its own separate copy of the guard, and only the thumbnail route's copy changed.
